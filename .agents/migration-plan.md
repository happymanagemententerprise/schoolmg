# Happy Man Academy — Full Migration Plan
> Generated by deep read of all four source files (app.js 4275 lines, data.js 3403 lines, index.html 1604 lines, styles.css 1343 lines) plus README, PROJECT-STATUS, and supabase/config.toml.

---

## Executive Summary

Happy Man Academy is a **zero-build-step, single-page vanilla JS application** — three files (index.html, app.js, data.js) plus a stylesheet — backed by Supabase. The frontend is a monolith: 4,275 lines of app logic and 3,403 lines of data/domain logic live in two giant script tags. The codebase has no module system, no bundler, no tests, and a DOM that is entirely server-rendered by string concatenation. Despite these constraints the app is architecturally clean: data.js exposes a synchronous cache API (the `Data` object), domain logic is split into named namespaces (`Academic`, `Progression`, `Growth`, `Timetable`), and the UI is role-gated with a simple view-router.

**Recommended path:** a four-phase migration — (1) file splitting into ES modules served via `<script type="module">`, (2) selective Alpine.js for simple reactive fragments, (3) Vite for a proper build pipeline, (4) React for the most complex interactive views — executed incrementally over 9–12 developer-weeks. The biggest single risk is the **circular global-state dependency** between app.js and data.js: every render function reads `currentUser` and calls `Data.*`, `Academic.*`, `Progression.*`, `Growth.*`, and `Timetable.*` without any import. Breaking those links is Phase 1's core challenge and must be done carefully to avoid regressions.

Total estimated effort: **9–12 developer-weeks** for one developer. Phase 1 is highest risk but lowest effort; Phase 4 is highest effort but highest long-term payoff.

## Phase 1: File Splitting Plan

### Goal
Convert the two monolithic files into ES modules without changing any observable behavior. No new dependencies. No build step. The app still runs from `python -m http.server 8000`.

### Design Decision: Shared Globals Strategy
Use a single `src/globals.js` that exports the mutable `currentUser` reference via a getter/setter pattern. All other modules import from `src/globals.js`. This avoids the need to thread `currentUser` through every function call and matches the existing implicit global contract.

### Shared Globals Strategy

`src/globals.js`:
```js
// src/globals.js
let _currentUser = null;
export const getCurrentUser = ()  => _currentUser;
export const setCurrentUser  = u  => { _currentUser = u; };

// Re-export DB for convenience so modules don't need to import data.js for it
export { DB } from './data.js';
```

Every module that needs `currentUser` does:
```js
import { getCurrentUser } from '../globals.js';
const currentUser = getCurrentUser();
```

The `renderView()` dispatch table in `nav.js` imports all render functions and calls them. The `auth.js` login/logout functions call `setCurrentUser`.

### Circular Dependency Analysis

One genuine circular dependency exists:
- `nav.js` needs to call `renderView()` which calls functions from all domain modules (admin, teacher, student, parent).
- Domain modules may call `showView()` from `nav.js` to navigate programmatically (e.g., clicking "View timetable" in admin classes navigates to the timetable view).

**Resolution:** Move `showView()` into `nav.js` and export it. Move `renderView()` into `nav.js` as well (it is just a dispatch table). Domain modules import `showView` from `nav.js`. `nav.js` imports all render functions from domain modules. This creates a hub-and-spoke pattern with nav.js at the center — no circular imports.

The only remaining near-circular: `report-drawer.js` calls `Academic.*`, `Data.*`, `Growth.*`, and `openDrawer()` from `nav.js`. Keep report-drawer.js as a leaf module that imports from nav.js (for `openDrawer`) and from data.js. No circular dependency.

### index.html Change Required

Replace:
```html
<script type="module" src="data.js"></script>
<script src="app.js"></script>
```
With:
```html
<script type="module" src="app.js"></script>
```

data.js currently uses `import { createClient }` at the top (ESM already). app.js uses no `import` or `export` statements. After splitting, app.js becomes the ES module entry point.

### Verification Approach
After each file is split:
1. Open `http://localhost:8000` in the browser
2. Check the browser console for import errors
3. Log in as each demo role (Admin, Class Teacher, Subject Teacher, HOD, Student, Parent)
4. Navigate to every view in that role's nav and confirm it renders without a console error
5. Perform one key action per domain: add a student, generate a timetable, save attendance, submit feedback, take a quiz

There are **no automated tests**. Verification is entirely manual browser testing. This is the biggest risk of the split phase.

**Effort:** 4 developer-days  
**Risk:** Medium — the global coupling is dense but the app has no tests, so regressions are caught only by manual testing  
**Reversibility:** Easy — git revert to the two-file version in under 5 minutes

## Phase 2: Alpine.js Integration Plan

### Design Decision
Use Alpine.js CDN (`<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3/dist/cdn.min.js">`) added to `index.html`. No build step needed. Alpine and the existing vanilla JS coexist: Alpine manages reactive fragments, vanilla JS continues to own large table renders and complex orchestration.

### Views / Components That Benefit from Alpine.js

| Component | Justification |
|---|---|
| **Login form error state** (`#login-error`) | Simple `x-show` bound to a reactive error string. Currently imperative (`err.hidden = false`). Alpine cleans this up with almost no code. |
| **Demo account buttons** | Already just data attributes + event listeners. An `x-data` block with `email`/`pw` state and `x-on:click` is cleaner. |
| **Password toggle** (`#toggle-pw`) | `x-data="{ show: false }"` + `x-bind:type` on the input and `x-on:click` on the button. |
| **Upload toggle pills** (`admin-upload-toggles`) | Currently rendered by `renderUploadToggles()` on every click. With Alpine, two reactive booleans (`testOpen`, `examOpen`) bound to toggle pills and labels — no re-render needed. |
| **Term badge** (`admin-term-badge`) | `x-text` bound to current term. |
| **Sidebar session label** (`sidebar-session`) | `x-text` |
| **Toast notification** (`#toast`) | `x-show` + `x-transition` with a `hidden` reactive flag. The `toast()` function sets the flag instead of directly toggling `.hidden`. |
| **Modal open/close** (all 13 modals) | Replace `openModal(id)` / `closeModal(id)` with Alpine `x-show` + `x-trap` (focus trap). Each modal gets `x-data="{ open: false }"` and buttons use `x-on:click`. |
| **Tab switcher in Admin People** (`#people-tabs`) | `x-data="{ tab: 'staff' }"` + `x-on:click` on tab buttons + `x-show` on each panel. Eliminates `bindPeopleTabs()` and the imperative active-class logic. |
| **Subject/Level filters in Admin Subjects** | `x-data="{ level: 'ALL', group: 'ALL' }"` + `x-on:change` to retrigger the draw function. |
| **Upload open/closed labels in Setup** | `x-text` and `x-bind:class` replace `updateUploadLabels()`. |
| **Daily attendance week/day selectors** | `x-model` on the `<select>` elements and `x-on:change` to call the existing `drawDay()` function. |
| **Student search input in Admin Overview** | `x-model="query"` + `x-on:input="renderAdminStudentTable(query)"`. |
| **Feedback submit/update buttons** | `x-data="{ submitted: false }"` + `x-bind:text` for the button label. |
| **Path card selection** (student pathway) | `x-data="{ chosen: '' }"` replaces the `$all('.path-card').forEach` click handler. |

### Views / Components to Skip

| Component | Reason to Skip |
|---|---|
| **Score tables** (subject scores, class report matrix, analytics table) | Generated by string concatenation from 10–200 rows. Alpine's template scanning would be slower than the current `innerHTML` blast. Not worth it — these are write-once renders, not reactive. |
| **Timetable table** | Same — large static render from a schedule object. |
| **Student report drawer contents** | Complex conditional rendering across 6 roles. Better as a React component in Phase 4. |
| **LMS quiz taker / question editor** | Complex multi-step state. Better as a React component in Phase 4. |
| **HOD department management** | Complex multi-form interaction. Better as a React component in Phase 4. |
| **Progression decisions table** | 40+ rows with per-row action buttons. Better as a React component in Phase 4. |
| **Leaderboard tables** | Static renders, no interactivity beyond rendering. Not worth adding Alpine. |

### Migration Steps (incremental — no big bang)

1. Add Alpine.js CDN link to `index.html` `<head>`. Confirm it doesn't break existing JS (it won't — Alpine is non-invasive).
2. Migrate the login form (`x-show` for error, `x-data` for password toggle). Test all demo logins.
3. Migrate the toast (`x-show` + `x-transition`). Update `toast()` to set an Alpine data property instead of `el.hidden`.
4. Migrate all 13 modals to `x-show` + `x-trap`. Remove the `openModal`/`closeModal` functions (or keep them as Alpine wrappers: `Alpine.store('modals')[id] = true`).
5. Migrate the Admin People tabs (`x-data` + `x-show` per panel).
6. Migrate the upload toggle pills.
7. Migrate the term/level/group filters in Admin Subjects.
8. Migrate the student search input.
9. Migrate the attendance day/week selectors.
10. Migrate path card selection.

Each step is a self-contained change to one area. If any step breaks something, revert it without affecting other steps.

**Effort:** 3 developer-days  
**Risk:** Low — Alpine.js is additive and non-breaking; existing JS and Alpine coexist  
**Reversibility:** Easy — remove the CDN link and undo the `x-data` attributes

6. Run `npm run build` and serve `dist/` to confirm the production build loads
7. Move `styles.css` to `src/styles.css` and add `import './styles.css'` in `app.js` (Vite handles CSS imports from JS)

## Phase 4: React Migration Plan

### Design Decision
Incremental component-by-component migration using a **shell architecture**: index.html keeps the app shell and vanilla JS views, while React mounts into specific `<div id="react-*">` mount points for the most complex views. This means vanilla JS and React coexist during the migration — no big-bang rewrite.

The React version of a view replaces the `innerHTML` render function. Navigation (`showView`) stays vanilla. The data layer (`Data.*`, `Academic.*`, `Progression.*`) is unchanged — React components call these synchronous functions directly. No GraphQL, no Redux, no new data fetching layer.

**State management:** React Context API only. The app's global state is `currentUser`, the session object, and a few per-view ephemeral states (selected tab, form values, modal open state). Context API handles this well without adding Zustand or Jotai. A single `AppContext` provides `currentUser`, `session`, and `term`.

**Routing:** Keep the existing `showView(pageId)` / `renderView(pageId)` pattern for top-level navigation. React Router is not needed — it would require restructuring the entire shell. Each React component is self-contained within its mount point.

### State Management — Context API

```jsx
// src/context/AppContext.jsx
const AppContext = React.createContext(null);

export function AppProvider({ children }) {
  const [currentUser, setCurrentUser] = React.useState(null);
  const session = currentUser ? Data.session() : null;
  const term    = session?.currentTerm ?? 1;

  return (
    <AppContext.Provider value={{ currentUser, setCurrentUser, session, term }}>
      {children}
    </AppContext.Provider>
  );
}

export const useApp = () => React.useContext(AppContext);
```

Per-view state (selected tab, form values, current week in attendance) stays local to each component via `useState`. No need for a global state manager — the Data cache is the source of truth and is synchronously accessible.

### Keep data.js Intact

`Data`, `Academic`, `Progression`, `Growth`, and `Timetable` are **not rewritten**. React components call them directly:

```jsx
function ClassPerformanceTable() {
  const { term } = useApp();
  const classes = Data.classes();   // synchronous, reads in-memory cache

  return (
    <table>
      {classes.map(cl => {
        const avg = Academic.classAverage(cl.id, term);
        // ...
      })}
    </table>
  );
}
```

Writes go through the existing `Data.*` async methods. After a write completes, call a local `setKey(Date.now())` to trigger a re-render (a simple cache-bust pattern — no need for SWR or React Query at this stage).

### Migration Strategy — Incremental Mounts

**Priority order** (highest complexity first, most user-visible benefit second):

1. `StudentReportDrawer` — called from 5+ views, complex conditional rendering
2. `ClassAttendance` — the most stateful view in the app (draft per-student-per-day-per-week, 3-state buttons, save + rollup)
3. `AdminProgression` — complex decision table with override buttons, password confirm, pool management
4. `QuizManager` (teacher) + `QuizTaker` (student) — multi-step dynamic form with question editor
5. `ClassOverview` + `ClassReport` — large tables with many per-row actions
6. `StudentDashboard` — multiple panels, growth XP, badges
7. All modals as shared `<Modal>` wrapper
8. Remaining views in order of complexity

In the existing view HTML (index.html), replace the inner content with a mount point:

## Risk Assessment Summary

| Phase | Key Risks | Mitigation | Reversibility |
|---|---|---|---|
| **Phase 1: File Splitting** | Dense global coupling between app.js and data.js; `currentUser` read in 40+ functions; `Data.*` called everywhere; no tests to catch regressions | Split one domain at a time (auth first, then utils, then admin domains); manually test each role after every file move; keep a tagged git commit of the working monolith | **Easy** — `git revert` to the two-file monolith takes < 5 minutes |
| **Phase 1** (continued) | `renderView()` dispatch table must be updated every time a new file is split | Build the `nav.js` dispatch table last, after all render functions are in their final files | Easy |
| **Phase 2: Alpine.js** | Conflict between Alpine's reactive DOM and vanilla JS `innerHTML` blasts; if a render function replaces innerHTML inside an Alpine-managed element, Alpine loses its bindings | Never use Alpine inside elements that are fully replaced by `innerHTML`; use Alpine only for elements with targeted, stable DOM (the modal backdrop, the toggle pills, the search input) | **Easy** — remove Alpine CDN link, strip `x-*` attributes |
| **Phase 3: Vite** | CDN-to-npm Supabase switch could expose latent import issues if the SDK API differs between versions; Vite dev server's port 8000 conflict with the existing Python server | Run `npm run dev` on a different port (8001) initially; pin the exact same Supabase SDK version as the CDN; test all Supabase table reads after the switch | **Easy** — remove package.json, revert data.js import line |
| **Phase 3** (continued) | Vite production build (`npm run build`) asset hashing and `<base href>` might break Cloudflare Pages deployment if the `wrangler.toml` `build.command` is not updated | Add `build.command = "npm run build"` and `build.output_directory = "dist"` to `wrangler.toml` before deploying | Easy |
| **Phase 4: React** | Stale cache data in React components — the Data cache is mutated by writes but React has no reactive subscription to it; components that read `Data.classes()` won't re-render when `Data.addClass()` is called | Every write operation must trigger a React state update in the calling component (a `setVersion(v+1)` pattern or pass a `refresh` callback); document this pattern in the codebase | **Medium** — each view can be individually reverted to vanilla `innerHTML` |
| **Phase 4** (continued) | The `_cache` object in data.js is mutated in place (e.g., `_cache.students.push(record)`); React's strict equality check for re-renders means components may not re-render | Either switch cache mutations to immutable updates (spread + replace), or use a `useEffect` + `subscribe` pattern; the former is cleaner but requires touching data.js writes | Medium |
| **Phase 4** (continued) | Score upload (`processScoreUpload`) is 200+ lines of complex async logic that reads from DOM (`$('st-score-subject').value`) directly; migrating this to React requires lifting all selection state into component state | Migrate `SubjectScores` and `ScoreUpload` as one React component so all DOM reads become React state reads | Medium |
| **All phases** | No automated test suite; regressions are caught only by manual testing | Write a minimal smoke-test script (can be a bash/PowerShell script that loads the page and checks for console errors via Playwright headless) before Phase 3; this is the single highest-leverage investment in CI coverage | Medium |
